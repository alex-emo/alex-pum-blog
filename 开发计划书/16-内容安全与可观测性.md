# OPT-16 内容安全兜底与可观测性

| 项目 | 内容 |
| --- | --- |
| 优先级 | P2 |
| 预计工时 | 4 h |
| 涉及文件 | `app/markdown_render.py`、`app/routers/admin_posts.py`、`scripts/`（新增监控）、Cloudflare 控制台 |
| 风险 | 低 |

## 问题

### 1. Markdown 正文无 HTML 清洗

`markdown_render.py` 渲染后直接交给模板 `|safe` 输出，**没有 bleach / nh3 之类的白名单清洗**。

当前"只有管理员能写"→ 风险自担，可接受。但这是一条**信任边界**：

- 将来若出现多作者、游客投稿、评论转 Markdown、外部文章导入，立刻变成存储型 XSS；
- `attr_list` 扩展允许写 `{: onclick="..." }` 之类，一旦有人能写 Markdown，就有执行面；
- 配合 OPT-04 的 CSP 才算双保险。

### 2. 第三方脚本

线上实测有 Cloudflare 自动注入的：

- `/cdn-cgi/scripts/.../email-decode.min.js`（邮箱混淆，见 OPT-10）
- `static.cloudflareinsights.com/beacon.min.js`（Web Analytics RUM）

它们不是代码里引入的，但**确实在给第三方发送数据**。作为"隐私友好"的个人博客，需要用户知情或改为自托管统计。

### 3. 无可观测性

- 无 uptime 告警：1G 内存的小机器 OOM、隧道断连、证书/隧道 token 失效，都只能靠你自己发现；
- 无错误日志聚合：`logger.exception` 打到 journald，但没人看；
- 备份成功与否也没有通知。

## 方案

### 1. HTML 白名单清洗（1 小时）

```python
import nh3  # 纯 Rust 实现，比 bleach 快，维护活跃
import re

ALLOWED_TAGS = {
    "a", "abbr", "b", "blockquote", "br", "code", "del", "div", "em",
    "h1", "h2", "h3", "h4", "h5", "h6", "hr", "i", "img", "kbd", "li",
    "ol", "p", "pre", "s", "span", "strong", "sub", "sup", "table",
    "tbody", "td", "th", "thead", "tr", "u", "ul",
}
ALLOWED_ATTRS = {
    "*": {"class", "id", "title"},
    "a": {"href", "rel", "target"},
    "img": {"src", "alt", "width", "height", "loading", "decoding"},
    "span": {"class", "style"},   # MathJax/KaTeX 需要
    "div": {"class", "style"},
}

def sanitize(html: str) -> str:
    return nh3.clean(
        html,
        tags=ALLOWED_TAGS,
        attributes=ALLOWED_ATTRS,
        url_schemes={"http", "https", "mailto"},
        link_rel="noopener noreferrer nofollow",
    )
```

注意：

- **MathJax/KaTeX 需要在 span/div 上写 `style`**，白名单里给这两个标签放开，其余标签不放开；
- `codehilite` 输出的 `<div class="codehilite">` 要保留 `class`；
- 清洗放在**渲染时**（写库前），这样历史文章不会每次请求都清洗；
- 若担心误删，先跑一次 dry-run：把现有 4 篇文章渲染后清洗，diff 一下看有没有内容被删。

### 2. 第三方脚本治理

| 脚本 | 建议 |
| --- | --- |
| email-decode | 关闭邮箱混淆（OPT-10），或被 CSP 白名单收录 |
| cloudflareinsights（RUM） | **关闭** CF Web Analytics，改用自托管统计（见下） |

自托管统计二选一（1 核 512M 都跑得动）：

- **GoatCounter**：单二进制 ≤ 10 MB，内存 ~10 MB，无 cookie；
- **Umami**：Node/Postgres，重一些；不推荐在 1G 机器上跑；
- **Plausible CE**：Docker 组合，1G 勉强。

推荐 **GoatCounter**，数据在自己手里，且无 cookie 横幅需求。

### 3. 可观测性（2 小时）

```bash
# 最轻方案：cron + curl + ntfy / Server酱 / Telegram Bot
*/5 * * * * curl -fsS -o /dev/null -m 10 https://blog.pum.org.cn/api/health || \
            curl -s "https://ntfy.sh/<你的topic>" -d "blog down at $(date)"
```

进阶（可选）：

- `systemd` 的 `Restart=always` 已有，但 **OOM 不会自动重启**——加 `RestartSec=5` 与 `MemoryMax` 监控；
- 日志：`journalctl -u blog --since today | grep ERROR` 每天推一次摘要；
- 备份：`scripts/backup.py` 成功/失败后发一条通知（在 systemd `ExecStartPost` / `OnFailure` 里挂）；
- Cloudflare 的 **Health Checks**（免费额度够用），比外部 cron 更早发现隧道问题。

### 4. 备份改进（半小时）

- 现在 `prune()` 只清理 `backups/` 里超过 N 天的文件，**没有异地备份**。1G 的机器挂了，备份和站点一起没。
- 加 `rclone copy backups/ remote:blog-backup`（或 rsync 到另一台机器 / 对象存储）。
- 定期（每月）**实际恢复一次**：解压 media、`sqlite3` 打开测试、`PRAGMA integrity_check`。
