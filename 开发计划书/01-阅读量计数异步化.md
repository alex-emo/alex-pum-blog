# OPT-01 阅读量计数移出请求路径

| 项目 | 内容 |
| --- | --- |
| 优先级 | P0 |
| 预计工时 | 2 h |
| 涉及文件 | `app/routers/pages.py:158`、`app/routers/public_posts.py`、`app/services/posts.py` |
| 风险 | 低（行为不变，只是改写入时机） |

## 问题

文章详情页在 GET 请求里同步写库：

```python
# app/routers/pages.py:158 附近
db.execute(update(Post).where(Post.id == post.id).values(views=Post.views + 1))
db.commit()
db.refresh(post)
```

三个副作用：

1. **写失败 = 页面 500**。本地只读挂载下访问 `/hello-world` 直接复现 `sqlite3.OperationalError: attempt to write a readonly database`。
2. **每次阅读一次写事务**。SQLite 单写者，`busy_timeout=15000`，热门文章会串行排队；1 核机器上这直接换算成 TTFB。
3. **页面不可缓存**。只要读路径有副作用，CDN / 浏览器缓存就变成"会少记一次数"，OPT-14 的边缘缓存也就无从谈起。

## 方案

推荐 **B（批量累加 + 定时落库）**，A 作为最小改动先止血。

### A. 最小止血（30 min）

```python
try:
    db.execute(update(Post).where(Post.id == post.id).values(views=Post.views + 1))
    db.commit()
    db.refresh(post)
except Exception:
    db.rollback()
    logger.warning("阅读量写入失败 post_id=%s", post.id)
```

页面照常渲染，计数丢了就丢了。**这一步必须做，无论是否采用 B。**

### B. 计数缓存 + 定时 flush（推荐）

1. 新增 `app/services/views.py`：

```python
# 进程内计数，单 worker 部署够用；多 worker 时换 Redis
_pending: dict[int, int] = defaultdict(int)
_lock = threading.Lock()

def bump(post_id: int) -> int: ...      # 返回 当前展示值 = db值 + pending
def flush(db: Session) -> int: ...      # 一次性 UPDATE ... WHERE id IN (...)
```

2. `pages.py` 渲染时用 `views.db + views.pending(id)` 得到展示数，不再 `commit()`。
3. 落库时机二选一：
   - FastAPI `BackgroundTasks`：请求返回后执行，注意要用**独立会话**，别复用 `request` 的 db；
   - `asyncio` 定时任务 / `apscheduler`：每 60 s 或累计 50 次触发一次。
4. 进程退出时（`lifespan` 的 shutdown）强制 flush 一次，避免丢尾数。

### C. API 同步改

`app/routers/public_posts.py` 里同样的 `views + 1` 走同一套 `views.bump()`。

## 回滚

方案 A 只需删掉 `try/except`；方案 B 把 `pages.py` 的 `views.bump()` 换回原来的 `db.execute(update(...))` 即可，无 schema 变更。
